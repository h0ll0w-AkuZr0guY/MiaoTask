# 架构与扩展

MiaoTask 把设备接入、任务执行和应用规则分开：同一个本地控制台管理多个设备，每台设备独立观察、执行与记录；新增应用通过活动包接入。现有淘宝活动以 0.0.9 的修复提交 `1846fdf` 为行为基线，结构调整保持其配置、停止、核验和实例限制。当前真实应用适配仍为淘宝，扩展接口不等于已经适配其他平台。

开发入口见 [DEVELOPMENT](DEVELOPMENT.md)，按能力查找可复用代码见 [REUSABLE_INTERFACES](REUSABLE_INTERFACES.md)。本页解释边界和设计取舍，调用签名集中在接口手册维护。

## 设计取舍

| 目标 | 当前做法 | 原因与边界 |
| --- | --- | --- |
| 保留原有行为 | 会话状态、循环、返回与重试分别提取；活动策略保留在原应用包 | 重构不同时改变任务语义，页面特征也不冒充所有应用的通用规则 |
| 新应用能复用执行能力 | manifest 声明应用身份、配置和活动工厂；活动实现解析、动作与核验 | 新增应用不需要复制服务、统计或前端；不同页面可替换入口与恢复策略 |
| 多设备互不误操作 | 一个工作区一个控制器与线程，物理设备有独占租约 | 网页选中项只负责展示，不能成为后台线程隐式操作目标 |
| 适配比例与不同显示屏 | 读屏返回当前尺寸和设备坐标，图像处理显式提供反向变换 | 缩放后的 OCR 坐标不能直接用于点击；逻辑显示屏和采集 ID 分开处理 |
| 执行中可人工调整 | 今日任务选择与失败预算持久化，调度前再次检查 | “执行 / 跳过”调整候选集合；已开始的一步安全结束后才应用新选择 |
| 扩展保持可追踪 | 配置记录来源、存储按设备和实例隔离、异常保留现场 | 页面、网络或系统差异可以定位；认证状态保留给用户处理 |
| 框架与活动分开交付 | 框架保留公共运行库，活动从官方 main 按需获取源码 | 活动修复合并后即可更新；新增第三方依赖仍需升级框架，活动不提供沙箱 |
| 多活动与多设备协作 | 单个设备拥有有序活动计划，设备工作线程彼此并行 | 同一屏幕始终由当前活动和所选实例控制，不能并发驱动同一手机 |

主流程为：`网页操作 → 指定工作区 Controller → 所选 Activity → 设备观察 / 动作 → 返回核验 → 当日记录`。配置和注册表用于装配，不参与跨设备共享运行状态。

## 目录与边界

```text
MiaoTask/
├── main.py                       # 稳定启动入口
├── backend/
│   ├── main.py                   # CLI 与装配
│   ├── bootstrap.py              # 开发集成入口
│   ├── core/
│   │   ├── config/               # 默认配置、分层加载与校验
│   │   ├── device/               # 驱动、实例、截图、OCR、坐标与接入契约
│   │   ├── execution/            # 会话、循环、返回预算、重试、守卫
│   │   ├── storage/              # 日累计、命名空间、旧记录接续
│   │   ├── plugins/              # 可信活动目录、兼容校验与安装事务
│   │   ├── service/              # HTTP、来源校验、静态路由、预览与托盘
│   │   ├── models.py             # 文本、坐标和任务数据契约
│   │   └── registry.py           # 应用与活动发现
│   └── app/
│       ├── common/               # 注入规则的任务行配对与跳转可用性
│       └── taobao/
│           ├── manifest.py       # 应用包名、用户空间与旧记录策略
│           ├── configs/base.json
│           ├── utils/            # 搜索与任务分类规则
│           └── activities/double11/
│               ├── manifest.py   # 注册元数据
│               ├── config.json   # 活动配置
│               ├── activity.py   # 策略组合
│               ├── entry.py      # 入口与赚能量菜单
│               ├── tasks.py      # 解析规则装配
│               ├── actions.py    # 执行策略
│               └── verify.py     # 核验策略
├── frontend/                     # 原生 HTML/CSS/JS，无 npm 构建
├── shared/                       # 公共静态资源约定；打包工具由构建流程填充
├── scripts/                      # 构建、审计与验证入口
├── tests/                        # 原有回归、架构契约与合成对照数据
├── docs/                         # 项目文档
├── build/                        # 本机构建环境、工具与临时输出，默认忽略
├── activities/                   # 本机下载或预装的活动源码与安装记录，默认忽略
├── .venv/                        # 本地开发环境，默认忽略
└── dist/                         # 本地便携包，默认忽略
```

活动源码与私人运行数据分开保存。便携版默认使用 exe 旁的 `activities/apps/<app_module>/`，源码运行使用仓库根的 `activities/`；安装记录 `installed.json` 与目录缓存 `catalog.json` 同在活动根目录。活动中心显示实际位置并可打开文件夹。该目录不进入源码提交，任务日记录仍在数据根的 `apps/<app>/activities/<activity>/...` 下。

路径统一由 `core.runtime.activities_dir()` 决定：`MIAO_ACTIVITIES_DIR` 可显式指定，设置 `MIAO_DATA_DIR` 时活动也隔离到该数据根的 `activities/`。默认 exe 目录不可写时回退到用户数据根的 `activities/`，首次可复制可读的预装活动；原 `plugins/` 安装在新目录尚不存在时复制迁移，原文件保留，已有新安装不被覆盖。显式活动路径不可写时直接报错，不静默改用另一位置。

`core` 不导入具体平台包，也不包含平台包名或活动名。注册表读取本地 manifest，再按声明的工厂装配活动。文本几何放在 core，避免读屏层反向依赖业务层。平台之间通过 `app/common` 共享业务算法。

允许的依赖方向：`frontend → HTTP → service → registry / execution / device / storage`，`app → core`，具体活动还可以依赖本应用工具和 `app/common`。core 通过配置、回调和活动方法使用业务能力，不能反向导入某个 app。`backend/bootstrap.py` 与根 `main.py` 保留既有导入和启动入口，应用适配不应再增加一套入口。

任务行配对、状态机和恢复流程按职责拆分，保留原有分支与默认值。活动入口和核验存在较多当前页面特征，继续留在活动包；没有强行把这些判断推广成所有平台的默认规则。

## 注册一个活动

平台目录包含 `manifest.py` 和 `configs/base.json`，活动目录包含 manifest、config 及活动实现。以现有 `taobao/activities/double11` 为实际参考。

```python
from backend.core.registry import ActivityMeta

META = ActivityMeta(
    app='sample', id='daily-tasks', label='每日任务',
    factory='backend.app.sample.activities.daily_tasks.activity:DailyTasksActivity',
    config='config.json', device_types=('uiautomator2',),
)
```

公开活动 ID 可以带连字符，Python 包目录使用 `daily_tasks` 等合法标识符；两者由 `factory` 显式关联。无需依赖 ID 推导 import 路径。

活动继承 `core.execution.activity.Activity`。会话对象持有设备、配置、控制句柄、记录和读屏器；实现 `default_config`、`parse_tasks`、`is_task_list`、`execute`、`verify`，并声明应用身份 `application`。原有 `ensure_list(auto_open)`、`recover()`、`scan()`、`run()` 方法保留。可以复用 `Navigator`，也可覆盖入口与恢复方法；不同页面不应直接复制淘宝坐标。

`run()` 调用 setup、通用循环及 finally 中的 teardown。通用循环负责候选选择、重试、不可用事实、进度核验与统计；认证和身份核对失败始终中断。当前默认导航器还需要活动提供主页、活动页、菜单、列表及官方入口的判定钩子，接口见现有 `EntryPolicy`；没有这些页面结构的活动应提供自己的有限恢复策略。

`TaskRules` 注入按钮、进度、描述和累计奖励词表及分类函数，共用行配对算法；特殊平台可直接替换解析函数。新增活动后重启服务即可被注册表发现，前端「应用与活动」读取同一目录。未安装活动包时，HTTP 和离线自检仍可运行，执行入口禁用。

manifest 和活动都是会被导入的 Python 代码，应随 PR 审阅。源码运行可以发现仓库内活动；默认冻结包只带 `backend.app.common` 与框架，已审阅的活动安装后加入同一个 `backend.app` 命名空间。原有绝对导入路径继续有效，共用框架不需要为每个活动重复打包。

## 活动分发与安装边界

默认构建模式为 `framework`，明确排除具体 app 代码和活动配置；`--include-activities` 提供兼容验证用的完整包，文件名另外标识。PyInstaller 的 `bundle-policy.json` 和构建清单记录包的模式、接口版本与内置活动。完整包与空框架都由同一源码构建，不以删除工作区源码的方式控制打包内容。

活动中心以官方仓库最新 main 为目录来源，按应用和活动展示，安装时仅获取目标活动及本应用共享源码。一次目录刷新和安装绑定明确的源码提交，避免下载过程中 main 更新导致文件来自不同版本。活动适配在 PR 通过检查并合并后即可被客户端获取，不依赖框架发版或额外的活动 Release。

目录静态解析 manifest，并读取活动 `compat.json` 声明的框架接口和 Python 主次版本；缺失新声明时不推测兼容。固定提交的文件经长度、普通文件模式与 Git blob 摘要核验后才进入暂存导入。用于旧活动过渡的兼容白名单按 manifest 摘要限定，不授予其他活动默认兼容。

安装顺序为：读取官方源码目录、核对所选身份与提交、获取所选文件并核对内容、验证路径与容量、核对 manifest 和工厂归属、暂存完整目标应用目录、实际导入工厂并加载配置、交换目录与原子写安装记录、重建服务注册表。安装器内部的文件清单/归档校验与离线构建样本用于复用同一事务，不要求维护者额外发布活动 ZIP。阶段验证失败不替换原安装；文件交换或记录写入失败尝试回滚原目录。这里覆盖可捕获错误，不承诺进程被强杀或断电后的事务恢复。

同应用多个活动可共享工具，但其共享文件清单和摘要必须一致。更新共享代码会影响其他已安装活动时拒绝安装，避免悄悄替换其他活动依赖；维护者需先协调同应用包版本。卸载只移除对应活动，最后一个活动卸载后清理应用目录，保留任务日记录。

安装、更新和卸载由 `ActivityCatalogHub` 的服务级门控制：检查全部设备线程空闲并设置安装中标记，再启动安装线程。各控制器启动设备操作、添加或移除工作区均经过同一门；暂停的执行仍算忙碌。安装过程中不会让某个设备继续使用待替换模块。完成后重新绑定每个控制器的注册表；已卸载活动从其计划移除，失去当前活动的设备断开并等待重新选择。每台设备仍独立持有配置、实例、任务选择与记录。

活动包含可执行 Python 代码，使用助手进程权限，内容核验不是隔离机制。产品活动源固定为官方仓库，不接受网页提交任意源码 URL，也不在安装时运行 pip。缺失框架接口或第三方依赖在暂存导入阶段拒绝，用户需更新框架。公共框架接口改变时需同步契约、兼容说明和接口手册；离线已安装活动仍可运行。

框架打包与活动获取是两条独立路径。维护者的本地 Release Builder 接受源码 ZIP、目录或 GitHub 链接，在隔离副本中汇总待发布贡献、测试并构建自包含框架 ZIP，默认递增末位版本，也可选择要预装的官方活动。预装源码保留在便携目录的 `activities/`，可独立更新，不加入框架二进制。输入无需 Git 元数据，原始源码不被改写，工具不创建远端发布。GitHub PR CI 和评审负责合入质量，不承担客户端活动下载。详细构建过程见 [BUILDING](BUILDING.md)。

测试中会临时注册第二个合成活动，验证框架无需改代码即可运行另一平台。这只证明扩展契约可用，不代表该示例已适配真实 App。

## 配置与数据

配置顺序为 `core/config/defaults.json → 平台 base.json → 活动 config.json → 用户覆盖`，JSON 与 YAML 都支持。同名顶层字段由后一层替换，不做嵌套对象的递归合并。`load_resolved` 返回只读快照及字段来源；运行接口保留字典配置，原有 JSON 覆盖文件和网页字段仍可使用。当前 schema 仍包含入口文案、搜索词和固定任务类型等既有字段；增加新类型或全新的配置形态需要同时调整校验、调度与界面，不能只在活动 JSON 中声明。

记录路径为：

```text
runtime/apps/<app>/activities/<activity>/daily/<date>/<device_hash>/instances/<instance_hash>/
```

便携版的数据根仍为 `%LOCALAPPDATA%/MiaoTask`，`MIAO_DATA_DIR` 仍可覆盖。设备、应用、活动、实例、日期分别隔离。只有明确声明 `legacy_storage=True` 的原活动会接续旧 `daily/` 记录：检查身份后复制状态、事件和失败现场，保留旧文件，首次完成后不再导入，避免重复累计。单独调用 `DailyState` 且不传命名空间时仍可读取旧布局。

`core/execution/task_policy.py` 管理通用任务选择和失败预算，数据由 `DailyState` 保存；任务身份由规范化标题、任务类型、总次数、浏览时长和目标应用契约生成，不使用屏幕位置、当前进度或临时按钮文字。标题或契约变化视作新任务，避免同位置替换后继承跳过。失败累计达到本轮配置上限后当天不再选择；用户选“执行”可清除该任务失败预算和手动跳过，安全策略、任务类型设置和已确认应用缺失仍有效。停止、身份错误和人工认证不按普通失败计数。

每个任务默认根据识别结果进入可执行或跳过集合，前端按钮只调整集合，不能直接启动或操作坐标。当前步骤不因切换而中断；调度器在下一安全选取点复核选择。完成和人工任务不能强制加入。任务控制请求携带工作区、任务身份和当前设备/实例/日期作用域，旧作用域必须拒绝。无法唯一识别的同签名任务不提供单独调整，避免对错误的任务生效。

不把应用安装状态跨实例共享。Android 用户空间的安装情况可能不同；当天不可用事实继续随各活动、实例保存，次日重新判断。

## 设备、屏幕与模拟器

`core/device/wifi.py` 负责 mDNS 广播读取、TLS 配对与指定地址连接。配对码走子进程标准输入，不进入命令行、快照或配置；连接后继续使用原驱动、包名与用户空间限制。

`emulators.py` 只调用已安装 MuMu 的只读实例查询，读取运行中实例的实际 ADB 地址，不猜端口、不启动或修改模拟器。`inventory.py` 对已授权连接读取设备身份，去重 USB、TCP 与 mDNS 别名。Android 优先使用真实序列号，无序列属性的模拟器使用 Android ID；无法核定身份时拒绝多设备租约，避免重复控制。

截图、读屏和输入都使用设备坐标。`ScreenReader` 随观察刷新宽高，过滤其他应用的背景窗口，横屏大图采用重叠区域 OCR，并把结果移回原图；竖屏保留既有宽度处理。自定义 `ImageProcessor` 的裁剪、缩放结果必须通过 `CoordinateTransform` 回映，缓存键也需反映策略。

`displays.py` 从 Android 焦点取得逻辑显示屏，通过系统的主显示设备 uniqueId 解析采集 ID；MuMu 的逻辑 ID、HWC 端口、ADB 截图序号不能互换。输入使用相同逻辑显示屏。映射失败不回退主屏，热插拔或显示变化会刷新映射。默认主屏仍使用原截图与点击路径。

`DisplayGeometry` 描述尺寸、安全边距及挖孔区域，约束点击与滚动；现有 Android 提取器读取窗口报告的可见系统栏和挖孔，元数据缺失时保留全屏坐标。尺寸随观察刷新，`rotation` 字段保留方向表达能力；当前窗口提取器不填充该字段，也不依赖它自动旋转图像。画面完全不可读取时停止输入，不据隐藏控件继续点击。登录、授权和支付仍由本人处理。未知机型的窗口布局、自由窗口和折叠屏姿态需要相应实测，不能仅以分辨率比例推断支持。

`DeviceBackend`、`DriverFactory`、`EndpointProvider` 和 `ImageProcessor` 是已定义的扩展接缝。当前服务仍显式接受 `uiautomator2`、`hmdriver2`，没有把新工厂自动接入网页；自定义图像处理器也需由读屏器创建方注入。新增驱动或屏幕策略应提交装配、身份、坐标和错误语义的完整适配，不能仅增加一个类就宣称支持。

## 多设备与服务

一个 `DeviceHub` 管理最多 8 个 `Controller`，一个本地 HTTP 服务和一套静态页面。每个控制器拥有独立工作线程、停止/暂停句柄、预览缓存、活动、实例队列及日记录。各设备线程并行运行，同一台设备内的应用分身仍串行。

`ActivityPipeline` 管理各控制器最多 16 项不重复的显式 `(app, activity)` 计划。计划保存和排序不启动手机操作；运行时逐个核定活动和驱动支持、加载对应配置，再顺序执行该活动的实例队列。仅任务/滚动等公共配置跨活动复用，入口文案和搜索规则来自当前活动。活动正常返回才推进下一项；停止、认证、身份不符或异常终止本设备流水线，其余设备继续。

同一应用的不同活动保留本设备明确选择的实例，不同应用各自记住实例队列。切换应用重新绑定 `ApplicationProfile` 并核定可用实例，原选择失效时停止，不能回退到另一个账号；没有明确选择且没有主实例时要求本人选择。连接另一台设备会清空旧实例计划，避免相同包名/用户空间 ID 在不同手机上指向不同账号。批量启动只复制活动计划和公共设置，不复制分身选择。

| 状态 | 所有者 | 隔离方式 |
| --- | --- | --- |
| 连接、执行与操作锁 | 设备控制器 / 适配器 | 每台一套，不共享“当前设备” |
| 物理设备租约 | DeviceHub | 序列号或 Android ID，连接别名不可重复占用 |
| 活动、实例与配置 | 各控制器 | 执行期间禁止切换，批量配置逐台校验 |
| 日累计与失败现场 | DailyState | 设备、应用、活动、实例、日期命名空间 |
| OCR 推理状态 | 设备执行上下文 | 每个工作区独立引擎，缓存数量有上限 |
| 日志 | `core/context.py` 上下文 | 工作线程明确归属，不能写入其他设备的记录 |
| 当前展示 | 浏览器页面 | 只影响查询目标，不改变后台执行目标 |

开始连接时先核定物理身份、取得独占租约，再初始化自动化驱动。重复别名连接失败，原设备继续工作。移除需等待设备操作结束；已移除控制器拒绝迟到的写操作。退出一次停止全部控制器，并在统一时间预算内等待和保存。

`Controller.lock` 保护内存快照，日记录另有锁，设备 I/O 使用适配器锁。磁盘和设备调用不放在界面状态锁中等待；预览拿不到设备锁就跳过这一帧，避免延迟停止和任务操作。任务线程和预览线程均带工作区上下文，日志路由与 OCR 引擎按该上下文隔离。

批量启动将命令交给各设备线程，不等待上一台执行结束。部分未连接、忙碌或配置不兼容的设备各自返回失败，其余继续；停止、认证和异常默认仅影响本设备。批量复制任务与滚动配置，不复制账号或分身选择。

## HTTP 与前端

既有 `/api/state`、`run`、`scan`、暂停、继续、停止、配置、实例、预览、诊断等路径保留，不带设备参数时服务默认工作区。多设备请求通过 `?device=<workspace_id>` 明确目标，未知 ID 必须拒绝；浏览器切换时丢弃旧请求和旧预览结果，不能将迟到响应显示成新设备状态。

* `GET /api/workspaces`：工作区概要；`POST /api/workspaces`：添加。
* `POST /api/workspaces/remove`：移除空闲工作区；`/api/workspaces/batch`：向显式设备列表提交并行操作。
* `GET /api/inventory`、`/api/emulators`：已连接设备去重与 MuMu 实例发现。
* `POST /api/wifi/pair|connect`：当前工作区无线配对与连接；`/api/open_app` 仅唤醒所选实例。
* `/api/session/status|start|pause|resume|stop`、`/api/preview` 为既有别名，`/api/stats` 和 `/api/tasks` 返回指定工作区快照。
* `POST /api/task_skip|task_execute` 调整当天队列选择，不启动线程；`task_scope` 变化后旧请求无效。
* `GET /api/plugins` 返回官方 main 的活动目录、源码提交、安装情况、实际 `activities_dir/source_dir` 与操作进度；`POST /api/plugins/install` 提交显式应用/活动 ID 与页面展示的完整 `source_commit`，由全局门控制固定提交安装；卸载提交应用/活动 ID。`POST /api/plugins/open-folder` 使用同样的写请求校验，仅打开服务已解析的活动目录，不接受浏览器指定路径。
* `POST /api/select_pipeline` 保存指定工作区的有序活动列表；`run` 可携带同结构 `activities`，每项必须有有效 `app` 和 `activity` 字符串，未知或空身份拒绝执行。
* `/api/shutdown` 退出整个服务；所有写操作仍校验 Host、Origin 与令牌。工作区 ID 不构成授权凭据。

前端 `device-manager.js` 管理设备标签和批量选择，`api.js` 统一附加设备 ID；任务判断和坐标留在后端。只为当前展示设备提供额外预览；后台任务按自己的观察周期取图。标签切换不新开端口或浏览器页面。旧静态路径保留，所有资源由固定白名单提供。

## 变更时需要同步的契约

| 变更 | 同步维护 |
| --- | --- |
| 公用方法、输入输出、异常或默认行为 | 调用者、[复用接口手册](REUSABLE_INTERFACES.md)、相关回归 |
| 新应用或新活动 | manifest、分层配置、入口 / 解析 / 执行 / 核验、当前适配范围 |
| 活动分发或运行库 | 分发清单、框架/Python 兼容声明、ZIP 校验、冻结导入、自检和安装门控 |
| 新设备后端或显示策略 | 接入装配、物理身份、实例、坐标、可停止性与不可读画面的边界 |
| 持久化字段或任务身份 | 旧记录兼容、跨日 / 跨实例隔离、诊断输出与迁移说明 |
| 网页操作或 HTTP 参数 | 后端校验、前端目标绑定、迟到响应处理和用户说明 |

未知 App、更多模拟器供应商、自动选择屏幕处理策略等属于后续适配。通用框架提供接缝，实际支持以有对应实现和覆盖证据的功能为准。

验证、构建与覆盖边界集中在 [BUILDING](BUILDING.md)，贡献前先读本架构，再读 [CONTRIBUTING](CONTRIBUTING.md)。
