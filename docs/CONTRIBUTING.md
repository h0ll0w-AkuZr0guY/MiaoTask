# 贡献指南

欢迎报告问题、完善文档、优化公共组件或适配新应用。开发前先读 [AGENTS](../AGENTS.md)、[ARCHITECTURE](ARCHITECTURE.md) 和 [REUSABLE_INTERFACES](REUSABLE_INTERFACES.md)，再按 [DEVELOPMENT](DEVELOPMENT.md) 准备环境。测试与打包命令集中在 [BUILDING](BUILDING.md)。

## 提交 Issue

先搜索已有 Issue，避免重复报告。同一 Issue 聚焦一个问题，使用仓库的「问题反馈」或「功能建议」表单。

| 类型 | 标题格式 | 内容 |
| --- | --- | --- |
| 问题反馈 | `bug(模块): 触发条件与异常` | 版本、环境、复现步骤、预期与实际表现、脱敏证据 |
| 功能建议 | `feat(模块): 希望支持的行为` | 使用场景、当前困难、期望行为和可接受范围 |

例如 `bug(search): 键盘收起后未继续返回任务列表`、`feat(device): 增加某类模拟器接入`。模块可用 `device`、`screen`、`task`、`search`、`ui`、`docs`，也可使用含义明确的名称。

问题反馈请说明：

1. MiaoTask 版本及运行方式（便携包或源码），电脑系统。
2. 设备型号、系统及目标应用版本；连接方式、横竖屏，是否使用分身或多设备。无需提供序列号、Android ID、IP、端口或配对码。
3. 从哪个页面开始，依次做了什么，问题是否稳定复现。
4. 预期结果、实际结果，以及是否已尝试重连或重新启动。
5. 必要的脱敏截图或日志片段。完整诊断包可能包含隐私，按 [SAFETY](SAFETY.md) 检查后再选择性提供。

功能建议不需要先写实现代码。涉及新平台、结构调整或默认行为变化时，先对齐目标、现有契约复用方式和兼容范围。

## 开发约定

### 确定改动位置

| 改动 | 位置 | 复用入口 |
| --- | --- | --- |
| 设备、连接、截图、屏幕与坐标 | `backend/core/device/` | 驱动、发现、几何与读屏契约 |
| 调度、停止、返回、日记录 | `backend/core/execution/`、`storage/` | 会话、导航、任务策略与存储 |
| 工作区、HTTP、预览 | `backend/core/service/` | DeviceHub、Controller 与请求上下文 |
| 平台与活动 | `backend/app/<app>/` | manifest、配置、解析、执行与核验策略 |
| 网页交互 | `frontend/` | 统一 API、设备和无线连接组件 |

公共组件说明见 [REUSABLE_INTERFACES](REUSABLE_INTERFACES.md)。新增应用应复用框架，通过策略表达差异，不复制 HTTP 服务、设备控制器或整份活动代码。`core` 不加入平台名称分支，前端不推断手机坐标和任务成功。

### 保持兼容

* 一个 PR 聚焦一个目的，避免夹带依赖升级、无关重构或批量格式调整。
* 保持配置默认值、CLI、HTTP 与日记录兼容；必要变化写明调用者影响、迁移和回退方法。
* 保持设备、实例、显示屏、统计与日志隔离；界面切换不能改变执行目标。详细不变量以 [AGENTS](../AGENTS.md#必须保持的不变量) 与架构为准。
* 操作与恢复必须有边界，完成必须有反馈；认证、登录和支付交给本人处理，不更换系统输入法。
* 新设备与新活动的支持范围以实际覆盖为准，不能从分辨率、静态截图或模拟用例推断全部兼容。
* 识别优先采用场景、词表与相对区域匹配；同义词、OCR误读等差异优先追加配置，不新增固定机型分支。模糊按钮词不能跨用到登录、支付和其他权限场景，具体约定见 [DEVELOPMENT](DEVELOPMENT.md#先补词表再扩策略)。

### 同步文档

| 变更内容 | 同步位置 |
| --- | --- |
| 操作方式或设置 | [USAGE](USAGE.md)；核心入口变化再更新 README |
| 职责、依赖、运行或数据模型 | [ARCHITECTURE](ARCHITECTURE.md) |
| 公共组件、接口、错误边界或示例 | [REUSABLE_INTERFACES](REUSABLE_INTERFACES.md)，与代码在同一 PR 更新 |
| 源码运行与扩展步骤 | [DEVELOPMENT](DEVELOPMENT.md) |
| 验证、打包、发布工具 | [BUILDING](BUILDING.md) |
| 待发布贡献 | [UNRELEASED](UNRELEASED.md) |

根目录保留项目入口与必要配置，说明文档放在 `docs/`。不为每个会话、版本或验证轮次创建重复文档。公开截图使用合成或脱敏数据；保留上游来源和第三方许可。

## 提交 PR

### 分支与标题

从目标集成分支创建独立分支，建议 `feat/<主题>`、`fix/<主题>` 或 `docs/<主题>`。AI 创建分支默认使用 `codex/<主题>`。

建议提交与 PR 标题使用 `type(scope): 简短说明`，也接受能明确表达改动的其他标题：

| 类型 | 使用场景 |
| --- | --- |
| `feat` | 新能力或新适配 |
| `fix` | 错误修复 |
| `refactor` | 保持行为的结构调整 |
| `docs` | 文档与公开说明 |
| `test` | 验证用例与测试工具 |
| `chore` | 依赖、工具和维护 |

例如 `fix(navigation): 收起键盘后继续返回任务列表`。标题描述最终变化，避免“更新一下”“修复 bug”等无法判断范围的措辞。

### PR 正文

可使用 [PR 模板](../.github/pull_request_template.md)，用自己的文字说明以下内容即可，不要求固定语言或标题：

1. **问题与结果**：复现条件、改动前后的行为，关联 Issue（可用 `Closes #123`）。
2. **影响与兼容**：模块、配置、旧数据、公共接口，以及停止和恢复行为；不涉及的部分可简述。
3. **实际验证**：执行过的检查及结果、未覆盖范围。真机记录型号和系统等非敏感环境；没有真机可注明，合理的本地用例仍可供评审。
4. **文档与贡献**：按影响同步文档，并追加待发布条目。

验证范围按改动确定，具体方法见 [BUILDING](BUILDING.md#验证修改)。行为变化补充对应回归，保留原有断言；纯文案或低影响展示修改不要求新增测试。涉及多设备、坐标、实例或数据时应覆盖相应隔离与失败路径。不得把模拟用例、静态推断或剪辑画面写作真机成功。

### 贡献条目

普通 PR 建议在 [UNRELEASED.md](UNRELEASED.md) 的 `## 待发布` 下追加一条或少量单行记录：

```markdown
* 【修复】搜索键盘阻挡时继续逐层返回任务列表 (#123 / @作者)
```

类别选用 `新增`、`优化`、`修复`、`文档` 或 `维护`，描述可独立理解的变化。PR 号创建后补充，也可先写关联 Issue 或作者。同一贡献只记一次；解决合并冲突时保留双方条目，不用整个文件覆盖。这里不写测试流水、设备信息或发布声明。缺条目或格式不同只给出提示，维护者可在合并前补齐；已有条目不能删除或改写，保留唯一的 `## 待发布` 区域。

### 本地与自动检查

安装开发依赖并准备 Node.js 后，在仓库根执行 `python scripts/check_project.py`，完成当前公开源码审计、离线回归及 Python / JavaScript 语法检查。无需 npm 构建、连接真机或生成 exe。详细环境见 [BUILDING](BUILDING.md)。

PR 使用同一入口，只有一个必需的 `check` 作业。代码或依赖有变化时自动重跑；只编辑标题和正文不会重跑整套测试。标题、正文分节与新增贡献条目只给出友好提示，不因措辞阻塞合并。测试失败、敏感或非公开文件、删除既有贡献，以及普通 PR 修改版本、发布历史或发布计划会阻塞，维护者审核后才能合并。CI 不发布 Release，不需要贡献者提供密钥。

### 提交前核对

* [ ] 职责和依赖符合架构，优先复用了现有组件。
* [ ] 旧配置、接口与日记录兼容；必要的迁移与回退已有说明。
* [ ] 已说明实际验证、结果及未覆盖范围，相关回归未被删除或削弱。
* [ ] 使用、架构、公共接口等文档已按影响同步，并追加待发布贡献。
* [ ] 差异不含设备标识、地址、账号、配对码、私钥、原始截图、日志、环境或构建产物。
* [ ] 未夹带版本修改、已发布历史修改、标签或发布操作。

## 合并与发布

普通 PR 只接受代码、文档与对应验证，不修改 `version.json`，不改已发布历史或 `.github/release-plan.json`，不上传 exe/ZIP 或构建环境。检查通过后仍由维护者评审合并。普通 PR 合并和推送标签不会发版。只有维护者或仓库机器人创建的同仓库发布准备分支可修改版本、发布计划和两份发布文档，且必须通过严格的四文件与发布就绪校验；普通贡献不能借用该例外。

活动规则合并到官方 main 后即可在客户端活动中心刷新获取。活动与应用的新增/修复不要求单独的活动 Release；涉及框架接口或第三方依赖时仍需框架兼容更新。贡献条目继续按统一规范追加，不能因此跳过回归和评审。

框架由维护者决定何时发布，默认使用独立的本地 Release Builder：

1. 在可视化 Release Builder 中选择源码 ZIP、目录或 GitHub 链接，不要求源码包含 `.git`；默认自动递增末位，也可选择递增中位或保留版本。
2. 工具复制清洁源码，在副本中汇总 `UNRELEASED.md` 到 `RELEASES.md` 并清空已收录条目；原始输入不变，目标版本仅写入构建副本，成功后记录供下次递增。
3. 可勾选预装官方活动，运行回归、构建带环境 ZIP 并检查实际 exe，保留日志与汇总后的源码供审阅。
4. 维护者验收后自行决定同步发布记录和上传。工具不自动提交、推送或公开发布。

构建方法及保留的可选 GitHub 云构建见 [BUILDING](BUILDING.md)。未合并的 PR 不收录；各分支的已合并贡献持续积累，汇总只清除已经收录的待发布条目，不删除历史。公开版本覆盖、附件替换和标签移动需另行明确授权。

## 使用 AI 参与

让 AI 先读根目录 [AGENTS.md](../AGENTS.md)，确认公共接口与边界后再修改。提供问题、约束和预期行为，避免提供凭据、私钥或未经脱敏的诊断。贡献者负责审阅生成代码、验证陈述及公开文件；AI 的推测不能代替核验结果。推送、合并与发布应有维护者明确授权。
